# 开奖后逐期学习自动化修复设计

## 目标

新澳门与香港开奖结果在北京时间约 21:34 完成后，系统以低资源、可重试、不可重复学习的方式完成：核验开奖结果、结算开奖前冻结预测、更新模型、生成复盘并冻结下一期四项高概率分类预测。

正常目标是北京时间 21:40 至 21:55 完成；数据源延迟时允许由 22:04 的兜底任务继续处理。网页读取不得触发训练。

## 触发策略

GitHub Actions 每天使用三个 UTC 定时表达式触发：

- 北京时间 21:40：UTC `40 13 * * *`
- 北京时间 21:50：UTC `50 13 * * *`
- 北京时间 22:04：UTC `4 14 * * *`

保留 `workflow_dispatch` 供故障恢复。三个任务调用同一幂等结算接口；如果较早任务已经成功，后续任务只验证已有冻结结果，不得重复结算或学习。

GitHub 定时任务可能延迟，三个错峰触发用于降低单次漏跑风险，不承诺秒级执行。

## 单次任务数据流

每次触发必须重新执行以下流程，不得持有开奖前生成的研究制品持续等待：

1. 从生产 Sites 接口重新同步香港和新澳门最新历史。
2. 针对每个彩种用本次同步的数据生成独立 Python 研究制品。
3. 分别调用签名写入接口，单次调用快速返回。
4. 未核验时记录为“等待核验”，本次正常结束，由下一时点重新同步后重试。
5. 已核验时先结算旧期，再学习，最后冻结下一期。
6. 对每个彩种单独执行健康检查，一个彩种失败不能取消另一个彩种已完成的结果。

## 幂等与一致性

- 任务 ID 由彩种、最新数据期号和研究制品哈希生成。
- 相同任务 ID 重放必须返回相同结果。
- 同一期冻结预测只能结算一次。
- 训练必须发生在本期评分之后。
- 新模型生成失败不得覆盖旧冠军或已有冻结预测。
- 未经核验的数据不得结算、学习或推进目标期。

## 健康检查

旧检查只验证存在四项事件，无法发现模型停在旧期。新检查必须对每个彩种验证：

- 开奖接口最新一期是否已核验。
- 若已核验，预测接口目标期必须严格晚于最新开奖期。
- 最新开奖期必须存在且仅存在一份复盘。
- 学习记录的 `settledIssue` 必须包含最新开奖期。
- 冻结预测必须恰好包含四个固定槽位。
- 不得包含号码预测。
- 重放同一任务后复盘数和学习次数不得增加。

未核验不是模型故障，应输出明确的“等待核验”状态；已核验但目标期未推进才是失败。

## 故障隔离与资源控制

- 香港与新澳门使用独立步骤执行和记录结果。
- 不再让 `capture` 在同一份旧制品上等待 60 分钟。
- 单次签名写入使用有限网络重试，只处理短暂的 429/502/503/504 等错误。
- 日常开奖任务不运行完整 Node/Python 测试套件；完整测试由代码变更验证执行。
- 每周全量规则搜索与每月随机模拟继续独立运行，不阻塞逐期开奖。

## 可观测状态

自动任务及健康检查使用四种明确状态：

- `awaiting_verification`：开奖源尚未满足核验条件。
- `settled`：旧预测已结算并生成复盘。
- `frozen`：下一期四项预测已冻结。
- `automation_error`：开奖结果已核验，但结算或目标期推进失败。

生产页面后续可读取这些状态；本次修复至少保证接口和 GitHub 日志包含可判定信息。

## 测试与验收

- 测试三个 cron 与北京时间映射。
- 测试日常任务不再使用 3600 秒等待。
- 测试每次重试重新同步并重新生成制品。
- 测试香港与新澳门故障隔离。
- 测试健康检查拒绝“已核验但仍停留旧目标期”。
- 测试未核验结果不会造成失败学习。
- 测试重复调用不增加复盘、学习或冻结记录。
- 运行完整现有测试、类型检查和构建。
- 手动触发生产任务，结算 2026216 并冻结 2026217。
- 最终核对生产 API、GitHub Actions 和移动端页面读取结果。
